# Android client and Windows host: plan

Status: proposal, 2026-10-11. Companion document: [android-and-windows-tasks.md](android-and-windows-tasks.md)
(the task breakdown that agents build from). Read AGENTS.md and CLAUDE.md first.

Two new ports that share no code with the Apple apps:

1. **Android client** (Kotlin, Jetpack Compose, Material 3 components styled with the Peering visual language), same job as `apple/MacCast`.
2. **Windows host** (Rust), same job as `apple/MacCastHost`, kept simple.

They must talk to the existing relay and, ideally, to the existing Apple apps on the other end
(Android to Mac host, iPhone to Windows host). So the wire protocol is the contract, and the first
deliverable is writing it down.

## 0. Decisions in one screen

* The contract is `docs/protocol.md` plus golden vectors generated by Swift. Nothing else counts as a spec.
* Do not bump `ProtocolInfo.version` (20). Android and Windows speak 20. Any addition is an optional
  field or a capability flag (the handshake demands exact equality, `ClientSession+Handshake.swift:38`).
* Android: minSdk 29 (platform TLS 1.3), platform JSSE for the control stream, OkHttp only for the relay
  WebSocket, `kotlinx.serialization` with a custom Swift-enum serializer, MediaCodec into a SurfaceView.
* Windows: Rust workspace. `rustls` (ring) for TLS, DXGI Desktop Duplication for capture, Media Foundation
  H.264 for encode, `SendInput` for input, `tray-icon` plus `egui` for UI, Velopack for install and update.
* v1 video codec from the Windows host is H.264 only. The Mac host defaults to HEVC
  (`HostModel+Capture.swift:24-26`), so Android needs HEVC decode or a small optional hello field (section 2).
* Relay: add FCM, add a Play Billing verifier, raise one field limit. All additive.
* v1 means: pair, see the screen, move the mouse, type, switch displays, reconnect, relay fallback,
  files browse and preview, agent chat with approvals. Terminal, audio, clipboard, window capture,
  review and commit screens are LATER.

## 1. Protocol contract

Everything below was read in the Swift and Rust sources named. Where a shape is inferred from how
Swift's synthesized `Codable` behaves rather than seen in a test, it is marked UNVERIFIED and must be
proved by a golden vector (SPEC-002).

### 1.1 Layers

| Layer | What | Source |
|---|---|---|
| Discovery | Bonjour `_remotedesktop._tcp`, TXT keys `id`, `name`, `v`, port 51515 | `ProtocolInfo.swift:39-47`, `ServiceDiscovery.swift:87-100` |
| Transport | TCP, `TCP_NODELAY` on every socket, TLS 1.3 only, mutual, self-signed P-256 | `TLSConfig.swift:30-96`, `HostServer.swift` start() |
| Framing | `u32 BE length` (kind byte plus payload), `u8 kind`, payload; 16 MiB cap checked before allocating; unknown kind is a hard error | `Framing.swift:109-175` |
| Messages | JSON in the payload (kinds 0x02..0x22), raw binary for video and audio frames | `Framing.swift:4-77`, `Handshake.swift:299-307` |
| Relay signalling | JSON over WebSocket to `wss://getpeering.app/` | `ProtocolInfo.swift:35`, `RelayProtocol.swift`, `relay/src/protocol.rs` |
| Relay control | TCP to `controlHost:controlPort`, send the 16 byte token first, then TLS runs end to end | `tcp_relay.rs:88-95`, `RelayControlTunnel.swift:36-100` |
| Relay video | One UDP socket, every datagram prefixed by the 16 byte video token, relay strips it | `udp_relay.rs:25-30`, `VideoDatagram.swift:10-27` |

### 1.2 Connections and roles

* LAN: two TCP connections to port 51515 on the host. The first frame after TLS is `connectionRole`
  (0x01) with a one byte payload, 1 control or 2 video (`Framing.swift:197-200`, `ClientSession.swift:303,500`).
  The video connection has no handshake of its own; the host checks that an authenticated control session
  with the same client key exists (`HostSession+Handshake.swift:42-62`).
* Relayed: ONE control stream. The client does not open a video TCP connection
  (`ClientSession.swift:429-430`, `usesRelayedSingleStream`). Video goes over the UDP lane, with the
  control stream as the fallback lane (`videoChunk`).
* The TLS roles never swap: the phone is the TLS client, the host is the TLS server, even when the host
  dialled out to the relay. Apple needs a loopback splice for this (`RelayControlTunnel.swift:36-100`).
  Android and Rust do not: write the 16 byte token on the raw socket, then start TLS on that same socket.

### 1.3 JSON rules (only defined by Swift code today)

The messages are Swift `Codable` output (`MessageCodec`, `Handshake.swift:299`). A non-Swift peer must reproduce:

* Enum with associated values: `{"caseName":{"label":value}}`. Unlabelled values use `_0`
  (verified: `ProtocolModelTests.swift:341` expects `{"setVideoEnabled":{"_0":false}}`). A case with no
  payload is `{"lockScreen":{}}` (UNVERIFIED). Decoding an unknown case fails the whole message, which is
  why capability flags exist (memory note "Unknown enum case reads as a malformed payload").
* Optionals: nil is an absent key, never `null` (`encodeIfPresent`). Accept both on input.
* `Data` is standard base64 with padding. `UUID` is uppercase hyphenated. Dates are `Double` seconds since
  2001-01-01 (no date strategy is configured; grep of `dateEncodingStrategy` found nothing).
* `CGSize` (`CaptureSourceDescriptor.pixelSize`) is a two element array `[w,h]` (UNVERIFIED).
* `Modifiers` is a bare integer (`RemoteCommand.swift:21-31`); `MouseButton` is 0/1/2; string enums use the case name.
* Relay signalling is different: tagged `{"type":"connectToHost",...}` with camelCase keys, hex strings for tokens
  and keys (`RelayProtocol.swift:51-65`, `protocol.rs:15-17`). Tokens are exactly 32 hex digits.
* Control payloads are capped at 64 KiB on receive (`ProtocolInfo.swift:32`); the sender is not stopped from
  exceeding it, so senders must chunk (clipboard, catalogue icons capped at 48 KiB each, `CaptureSource.swift:222`).

### 1.4 Handshake and pairing, in order

1. TLS 1.3, client presents its certificate (host verify block accepts any, `TLSConfig.swift:47-49`).
2. Client sends `connectionRole`, then `clientHello` JSON (`Handshake.swift:3-70`): `clientID`, `clientName`,
   `protocolVersion`, `wantsPairing`, optional capability flags, optional `resumeSource`, `lostPairing`.
3. Host checks version equality, id lengths (256 bytes), takes the client key from the TLS certificate and never
   from a message, rejects a pinned id with a different key (`HostSession+Handshake.swift:64-100`).
4. Host sends `serverHello` (`Handshake.swift:73-176`): `serverID`, `hostName`, `protocolVersion`, `alreadyPaired`,
   many optional `supports...` flags, `macAddresses` only when already paired.
5. Client compares versions (`ClientSession+Handshake.swift:38`), checks `serverID` against the id it dialled (:49),
   checks its pin (:58), and refuses an unpinned host that claims `alreadyPaired` (:64).
6. Already paired: both sides become ready. Unpaired: SAS pairing.
7. SAS (`PairingSAS.swift`, `ClientSession+Handshake.swift:81-181`, `HostSession+Handshake.swift:167-241`):
   commit order is client `pairCommit`, host `pairCommit`, client `pairReveal`, host `pairReveal`. Commitment is
   `SHA256("MacCast-Pairing-commit-v1" || ephemeralPub || nonce)` (:28,:35). Ephemeral is a P-256 public key in
   x9.63 form (65 bytes), nonce 32 random bytes. Transcript (:113-134) is a sequence of `u32 BE length || bytes`
   fields: SAS domain string, `u16 BE` version, clientID, serverID, client eph, server eph, client nonce, server
   nonce, server identity public key (taken from the TLS certificate the client received). Code is the first
   four SHA-256 bytes as `u32 BE` modulo 1,000,000, zero padded to 6 digits (:65-78). No key agreement is
   computed; the ephemeral keys only feed the transcript.
8. Client sends `pairConfirm{accepted, proof?}`. `proof` is `HMAC-SHA256(secret, "MacCast-Pairing-proof-v1" ||
   transcript)` where `secret` came from the host QR `peering://pair?code=NNNNNN&secret=<hex>`
   (`PairingPayload.swift:65-93`, `PairingSAS.swift:51-63`). No proof means the host asks its user to approve
   (`HostSession+Handshake.swift:258-270`). Host answers `pairResult`; both pin the other key only after success.
9. Ready: client pings once a second (`ClientSession+Liveness.swift:9`); catalogue (0x07) is pushed unsolicited by
   the host shortly after connect and may arrive after the first pong (AGENTS.md trap 27).

Host QR content: `https://getpeering.app/mac?id=<UUID uppercase>` (`PairingPayload.swift:47-56`).

### 1.5 Identity and pins

* Key: P-256. Pin value is the 65 byte uncompressed point `0x04||X||Y` (`SelfSignedIdentity.swift:37`,
  `PeerPinning.swift:8-20`). It is called SPKI in the Swift but is the raw point, not the DER SPKI.
  The Swift comment claims the two sources are identical; a vector must prove that
  (`subjectPublicKeyInfoBytes` at `SelfSignedIdentity.swift:150`). UNVERIFIED.
* Certificate: self-signed, ECDSA/SHA-256, CN is the device name, O=Peering, not-CA, digitalSignature, EKU
  serverAuth (host) or clientAuth (client), valid from now minus 1 h for 10 years, regenerated every launch
  (`SelfSignedIdentity.swift:215-241`). Peers pin the key, not the certificate.
* Pins are `{deviceID: key}` stored in the OS secret store (`PeerPinning.swift:24-110`). Comparisons are constant time.
* Relay proofs: ECDSA P-256 over SHA-256, DER signature (not the 64 byte form), hex encoded
  (`SelfSignedIdentity.swift:82`). Payload strings: `peeringd-host-registration-v1\n<id>\n<unixSeconds>` and
  `peeringd-client-registration-v1\n...` (`RelayDeviceProof.swift:17,30`); referral variants :44-49. The relay
  accepts timestamps only within a few minutes of its own clock (`RelayHostRegistration.swift:150-153` comment).

### 1.6 Relay signalling

Client messages: `registerHost`, `connectToHost`, `requestPeerAddress`, `hostPresence`, `ping`, `referralStatus`,
`redeemReferral`, `notifyDevice` (`protocol.rs:19-212`). Server messages: `registered`, `sessionReady`,
`hostOffline`, `peerAddress`, `hostPresence`, `referral`, `pong`, `error` (`protocol.rs:215-283`).

* Host: open the WebSocket, send `registerHost` with proof, keep the socket open (that is presence), ping every
  25 s, reconnect with backoff 1,2,5,10,30 s (`RelayHostRegistration.swift:137-200`). On `sessionReady` push, dial
  `controlHost:controlPort` and write `controlToken`.
* Client: `connectToHost` with `hostId`, `clientId`, version, optional `plan`, `jwsRepresentation`, client proof.
  `quotaExceeded` is an `error` code (`ClientSession.swift:286`). Unverifiable receipts mean the free allowance
  (30 min per rolling 24 h, `config.rs:184-219`), never a refusal.
* Direct path: `requestPeerAddress{videoToken}` is polled (8 tries, 150 ms) and `peerAddressUnknown` is the normal first
  answer (`RelaySignalling.swift:132-160`).

### 1.7 Video lane (relayed and direct)

* Keying: the host sends `videoKey{secret 32 bytes}` over the TLS control stream in answer to `videoKeyRequest`
  (0x19/0x1A, `ClientSession+Video.swift:97,121-139`). Per direction key =
  `HKDF-SHA256(ikm=secret, salt="pl.dmq.peering.video-datagram", info="video client-to-host" | "video host-to-client", 32)`
  (`VideoKeySchedule.swift:19-45`).
* Datagram sent: `token(16) || counter(8 BE) || ChaCha20-Poly1305 ciphertext || tag(16)`; nonce is 4 zero bytes then the
  counter BE; counter starts at 1 (`VideoDatagramSealer.swift:25-60`). Received (relay stripped the token):
  `counter || ciphertext || tag`. Max datagram 2048 (`VideoDatagram.swift:26`). Plaintext is a normal framed message
  (`Frame`), cut into `videoChunk` pieces of at most 1024 bytes (`VideoFallback.swift:41-96`): header
  `innerKind(1) frameID(4) index(2) count(2)`.
* Replay window of 64 with a bitmap; check without mutating, commit only after authentication
  (`VideoReplayWindow.swift:8-60`). Reassembly: a chunk of a newer frameID discards the one in progress.
  One opener per lane (`VideoDatagramOpener.swift:7-12`).
* A datagram holding only the 16 byte token is a bind and is not forwarded; both ends send one and repeat it as a
  keepalive (`VideoDatagram.swift:17`).
* Direct path: `directProbe` (0x1B) sealed datagrams to the address learned from `peerAddress`, every 250 ms for
  12 attempts, then every 5 s, re-asking the relay every 12 attempts (`ClientSession+DirectPath.swift:36-65`).
  The receiving end learns the peer address from the source of a datagram that authenticates. The host side is
  `VideoDatagramLane.swift` (both ends knock).
* Fallback onto the control stream (`VideoFallback.swift:183-282`): 3 s without a picture while a pong arrived in the
  last 5 s, then `videoTransport{control}` (0x18); repeat every 5 s until a picture arrives; return after 5 s hold
  and 2 pictures on the primary lane. The host may decline and caps rate at 2000 kbps in fallback.

### 1.8 Capability flags

`ClientHello` and `ServerHello` carry optional booleans (`Handshake.swift`). nil means no. The sender must not use a
feature unless the other side declared it. The Windows host declares only what it implements. The Android client
declares `supportsAgentChat` and `supportsAgentPermissionModes`, `supportsAgentUsage` when built, nothing else
at first (text focus, field state, pointer report, clipboard images are all LATER). Proposed additive fields
(the Swift decoder ignores unknown keys, so shipped apps are safe): `ClientHello.clientPlatform`,
`ClientHello.videoCodecs` (ordered list), `ServerHello.hostPlatform`. The Mac host must be taught to read the
codec list (a Mac host change, no version bump).

Input semantics that leak platform:

* `keyDown/keyUp.keyCode` are macOS virtual keycodes (`InputEncoding.swift:54-76`: 54..63 are modifiers). Windows
  host maps them to scancodes; Android maps `KeyEvent` codes to them. The table is a shared vector (SPEC-005).
* Modifiers are bits 17..20 (`RemoteCommand.swift:8-16`). Windows host maps Command to Ctrl by default.
* Coordinates are normalized 0..1 of the captured source, absolute. There is no relative mouse, so trackpad mode
  is a client side virtual cursor.
* Paths in the file and agent browse protocol are POSIX shaped: the iOS UI requires a leading `/`
  (`FileBrowserPanel+Header.swift:160`), `permissions` is a 10 character `ls` string
  (`TerminalWire.swift:50-60`). The Windows host presents `/C:/Users/me` and a `/` that lists drives.

### 1.10 Gaps that need a written spec

Deliverables, in order: `docs/protocol.md` (SPEC-001), golden vectors generated by a Swift test
(`docs/protocol/vectors/*.json`, SPEC-002) so a wire change shows up as a diff, key map tables (SPEC-005), and a
relay conversation transcript (SPEC-004). Items only the Swift code answers today: the JSON rules in 1.3, the

sends first after ready (its quality tier, `ClientSession+Commands.swift:9-28` plus `VideoFallback.swift:214`),
there is no client request for a keyframe (so loss on the datagram lane lasts until the next keyframe, 2 s,
`VideoEncoder.swift:211`), the exact behaviour of `resumeSource`.

## 2. Video pipeline

What the Apple host emits (`VideoEncoder.swift`, `VideoWire.swift:11-164`):

* HEVC by default, H.264 if the GPU cannot (`VideoEncoder.swift:190-193`); 60 fps default; low latency rate control,
  real time, B-frames off, keyframe every 2 s and on demand; bitrate default `pixels*0.12*fps` clamped 4..30 Mbps
  (:444-447); client may set 2/8/20 Mbps tiers and `setStreamQuality` up to 100 Mbps (`StreamQualityLimits.swift:5`).
* Samples are AVCC (4 byte length prefixed NALs). Parameter sets are out of band in `videoConfig` (0x09): SPS, PPS for
  H.264; VPS, SPS, PPS for HEVC. A config is sent only when it changes; `sourceID` tells sources apart.
* `videoFrame` (0x0A) payload: 25 byte header (flags, width, height, pts value i64, timescale i32, data length) then
  data. The keyframe flag is bit 0.
* Audio: `audioConfig` and `audioFrame`, raw interleaved float32 PCM (`VideoWire.swift:197-294`).

Android decode: MediaCodec wants Annex-B with start codes. AVCC to Annex-B is replacing each 4 byte length with
`00 00 00 01` in place (same size). `csd-0`/`csd-1` come from the parameter sets with start codes added (HEVC: one
`csd-0` of VPS+SPS+PPS). Set `KEY_LOW_LATENCY` (API 30) and `KEY_PRIORITY=0`, render to a SurfaceView with
`releaseOutputBuffer(idx, true)`, no output queue. Rebuild the codec on any new config. HEVC hardware decode is
common but not guaranteed: check `MediaCodecList`; if absent, set the new `videoCodecs` hello field; until the Mac
reads it, the manual fallback is the host's stored codec setting (`HostModel+Capture.swift:24`). Not verified on a
device: whether pinch zoom works on a SurfaceView transform (fallback TextureView, one more frame of latency).

Windows encode: Media Foundation H.264 encoder MFT, hardware first (`MFTEnumEx` with the hardware flag exposes
NVENC, Quick Sync and AMF MFTs), Microsoft software encoder as fallback. Settings: low latency mode, no B-frames,
CBR with a one frame VBV, GOP 2 s, force keyframe attribute on demand. Pipeline with no CPU copies:
`IDXGIOutputDuplication::AcquireNextFrame` to a D3D11 texture, `ID3D11VideoProcessor` BGRA to NV12, MFT via
`IMFDXGIDeviceManager`. MFT output is Annex-B: split into NALs, lift SPS/PPS into `videoConfig`, rewrite to AVCC
(iOS needs AVCC and out-of-band sets, `VideoRenderer.swift:300-345`). HEVC from Windows is LATER (needs a vendor
HEVC MFT or an installed extension; unverified per machine). Not verified: MFT behaviour on each vendor, and
that a duplication on hybrid GPU laptops needs the device created on the adapter that owns the output.

Latency design (both sides): `TCP_NODELAY` everywhere; bounded send queue of one frame, drop deltas when the socket
backs up and always keep a keyframe (mirror `VideoDropPolicy`, `VideoWire.swift:299-313`); never buffer on decode;
timestamps from the wire used only for ordering. Duplication yields no frames on a still screen, same as ScreenCaptureKit;
the client's silence rule (3 s) then asks for fallback and the host must decline like the Mac does when it has
produced nothing recently (`VideoFallback.swift:244-247` comment).

## 3. Android app

SDK: minSdk 29, targetSdk current. Dark only, no dynamic colour: Material 3 components with the palette, surfaces, outlined cards and type from the design guidelines (decision 1). Package `pl.dmq.peering`.

Modules (Gradle, version catalog):

* `core:wire` pure Kotlin/JVM: framing, message models and serializers, SAS, HKDF, sealer/opener, replay window,
  chunk reassembler, fallback policy, input mapping. All logic lives here or in the next two modules so JUnit runs it.
* `core:session` pure Kotlin: connection state machine, reconnect ladder, video lane manager, quality policy,
  agent and file state holders. Depends only on interfaces for sockets, clock, keystore.
* `core:platform` Android: Keystore identity, SSLSocket factory, NSD, OkHttp signalling, DatagramSocket, MediaCodec,
  Play Billing. Thin.
* `feature:*` Compose screens: connect, remote, agents, files, settings, paywall. State holders are `ViewModel`s that
  only wrap `core:session` flows.

Architecture: unidirectional data flow, coroutines and `StateFlow`, one session scope per connected host. Networking
is blocking sockets on `Dispatchers.IO` with one reader coroutine per connection and a `Channel` writer so command
coalescing (`CommandCoalescer.swift`, mouse move at 60 Hz, scroll accumulates) sits in one place.

Identity and TLS: Keystore EC P-256 non-exportable key; `KeyGenParameterSpec.setCertificateSubject/NotBefore/NotAfter`
yields the self-signed certificate. UNVERIFIED: whether the Mac's listener accepts a client certificate without the
clientAuth EKU (its verify block returns true unconditionally, so likely yes); fallback is BouncyCastle signing the
certificate with a Keystore-backed `Signature`. TLS: `SSLContext.getInstance("TLSv1.3")`, trust manager records the
leaf key and compares to the pin when one exists (first pairing accepts, as `TLSConfig.swift:87-91`).

Input mapping: touch modes trackpad (virtual cursor, tap click, two finger tap right click, two finger scroll, long press
drag) and direct (absolute). IME text goes as `textInput` (Unicode); hardware and special keys go as macOS keycodes
through the SPEC-005 table; a modifier bar and shortcut bar sit above the keyboard.

Screens (mirror `HostPickerView.swift:9`, tabs connect, servers, sessions, faq, settings): bottom navigation with
Connect, Sessions, Settings (FAQ inside Settings; Servers/SSH is SKIP). The session screen is a full screen canvas with a
sheet hub (Sources, Agents, Files, Settings; Terminal later), matching the iOS `RemoteScreen` panels. Window size classes
switch the sheet to a side panel on tablets. The visual language comes from `wiki/DESIGN.md`, adapted where Material 3 requires it (decision 1).

Agent chat UI: transcript list with row types (user, streamed markdown, tool card, diff block, plan steps, subagent),
approval sheet, composer with permission mode and model menus, queue, interrupt. State logic ports from
`MacCastKit/AgentTranscript.swift` (256 lines) and friends into `core:session`.

File browser: breadcrumb, list, preview for text and images, download through the Storage Access Framework, upload through
the document picker.

Notifications and FCM: Android registers by sending `registerPushToken` with the bytes `"fcm:" + token` (UTF-8). The host
hex-encodes any bytes without inspecting them (`TerminalSessionManager.swift:227-236`), so the shipped Mac host needs no
change; the relay detects the prefix (section 5). Approvals from the notification are v1.1.

Billing: Play Billing Library, subscriptions plus a lifetime product mirroring the iOS products
(`StoreManager.swift:53-56`; whether Play accepts the same ids is not checked). The app sends `playPurchaseToken` and
`playProductId` in `connectToHost` (section 5). Product rule: every feature free, relay time free 30 min per day, paid unlimited.

Build and CI: Gradle Kotlin DSL, JDK 17, `./gradlew test` for JVM logic, lint, assembleDebug; release bundle signed from
secrets and uploaded to the internal track. Terminal emulator: Termux's terminal libraries are a candidate, license
UNVERIFIED; fallback is porting `TerminalScreen*.swift` (about 550 lines).

## 4. Windows host

Workspace `windows/`:

* `crates/peering-wire`: framing, messages, SAS, key schedule, sealer/opener, chunking, fallback decisions. No OS
  dependency, builds and tests on Linux CI.
* `crates/peering-core`: session state machine (`HostSession` port), pairing service, pin store trait, relay
  registration loop, video lane, command dispatch to traits. No OS dependency.
* `crates/peering-platform`: Windows only: capture (DDA), encode (MF), input (`SendInput`), DPAPI store, mdns glue.
* `crates/peering-agent`: process spawning, Claude Code stream parser, session manager, git (portable; uses `tokio::process`).
* `crates/peering-files`, `crates/peering-terminal` (ConPTY via `portable-pty`).
* `host`: binary with tray (`tray-icon`, `muda`) and a small `egui` window for QR, code, devices, settings. Chosen over
  Tauri or Slint because it is one binary with no webview and no licence question; accessibility is weaker, accepted.

Capture: DXGI Desktop Duplication per monitor (no capture border, dirty rects, direct D3D11 texture). Windows.Graphics.Capture
is reserved for single windows (LATER). Per-Monitor-V2 DPI awareness in the manifest, otherwise coordinates are virtualised,
the Windows twin of the `CGDisplayPixelsWide` trap (AGENTS.md trap 10).

Input: `SendInput` with `MOUSEEVENTF_ABSOLUTE|VIRTUALDESK` mapped from the normalised point through the current source
rectangle; wheel in multiples of 120 with accumulation; text via `KEYEVENTF_UNICODE` per UTF-16 unit; keys via scancode from the
macOS keycode table; release everything on disconnect (`InputInjector.swift:233` `releaseAll`); mouse down/up/keys never coalesced.
Limits stated up front: input and capture fail on the UAC secure desktop and the lock screen, and input cannot reach elevated
windows from a non-elevated host. v1 accepts this and shows a notice (`notice` frame, 0x10). A `uiAccess` signed build is LATER.

Switching on Windows: monitors yes (catalogue `displays`, source `display(u32)` using a stable id from the display config target;
rebuild the duplication and send a new `videoConfig`). Windows as sources LATER (`window(u32)` is an `HWND`, fits 32 bits).
Applications (`application(Int32)` composited by pid), mosaic, virtual displays (needs a signed indirect display driver): SKIP.
Virtual desktops: listing and jumping by index uses undocumented COM that changes between builds, SKIP; the left/right chord
(`Ctrl+Win+Left/Right` via `SendInput`) is LATER and cheap. Duplication follows whatever desktop is showing.

Identity and storage: key and pins under `%LOCALAPPDATA%\Peering Host`, encrypted with DPAPI. mDNS advertise
`_remotedesktop._tcp` with TXT `id`, `name`, `v`. Listener on 51515, plus the outbound relay registration, so a blocked inbound
port still works through the relay.

Agent sessions: the Mac host spawns CLIs, one process per chat for Claude Code with stream-json in and out and a permission
prompt tool over stdio (`ClaudeCodeAdapter.swift:71-83`), one process per turn for Codex and OpenCode (`PerTurnAdapter`,
`CodexAdapter.swift:18-32`). The event parsers live in `MacCastKit` (`AgentClaudeStream.swift` 362 lines, Codex 212, OpenCode
179), so they must be re-implemented in Rust against recorded transcripts. Windows needs: `CreateProcess` without a console
window, piped stdio, a Job Object to kill the tree, binary lookup on `PATH` and common install dirs (`.cmd` shims need
`cmd /c`), `git.exe` for changes and commit. Claude Code on native Windows needing Git for Windows is from memory, not verified.
No login shell concept, so the environment is the host's own, restarted after installing a CLI.

Terminal: ConPTY (`CreatePseudoConsole`) through `portable-pty`; the wire carries raw VT bytes (`TerminalWire.swift:135-181`), so
the Android emulator needs no change. LATER.

Packaging: an unsigned installer and documented build from source (decision 6); updates are LATER (Velopack or WinSparkle, unverified). Autostart through an `HKCU\...\Run` value. Firewall: per-user install cannot add a rule; the OS prompt
appears on first listen; a "Fix firewall" button runs an elevated `netsh`. Signing: none; the README explains the SmartScreen warning.

## 5. Relay changes (all additive, shipped iOS unaffected)

1. FCM sender beside `apns.rs`: `ServerMessage` unchanged; `notifyDevice` unchanged on the wire. A token whose decoded bytes start
   with `fcm:` goes to FCM HTTP v1 with a service account OAuth token (RS256 JWT through `ring`, cached 45 min like APNs'
   JWT, `apns.rs:42`). Payload carries `hostId`, `source`, `agentSessionId`, `agentApprovalId`, `category` as data keys.
2. Raise `device_token.len() > 128` (`signalling.rs:871`) to 1024 hex characters; an FCM token plus prefix is about 330 hex
   characters and would be rejected today. Keep the other limits.
3. Play Billing verifier `playbilling.rs` parallel to `storekit.rs`: optional `playPurchaseToken` and `playProductId` fields
   read leniently like `jws_representation` (`protocol.rs` `optional_text`); verdict maps to `Plan`; unverifiable means free;
   per session cache. Verification is an online call to the Google Play Developer API with a service account (the exact endpoints,
   `purchases.subscriptionsv2.get` and the one-time product equivalent, must be confirmed against current docs). This breaks the
   storekit module's "no network" property, accepted because Play's signed data has no expiry; fail closed to the free allowance,
   cache for an hour. Bind a purchase to a device by setting the Play obfuscated account id to the SHA-256 of the device public key
   and requiring a match when a client proof is present.
4. Nothing in `registerHost`, `sessionReady`, the TCP splice or the UDP forwarder assumes Apple. `ConnectToHost` and `RegisterHost`
   carry `protocol_version`; confirm the relay does not reject 20 from new peers (it must not; unverified beyond the field existing,
   `signalling.rs:180-190`).
5. Optional refactor: move `protocol.rs` message types and `device_proof` payload functions into a small crate the Windows host also
   depends on. Only after the relay suite is green; not on the critical path.
6. Tests: extend `relay/tests/end_to_end.rs` for FCM routing with a fake sender, token limit, and Play verdicts with a fake verifier.

3. **Mac host changes.** Not answered. The rule stays: `apple/` is not touched. The exact proposed patch (reading `videoCodecs`, sending
   `hostPlatform`, additive only) is in [mac-host-patch.md](mac-host-patch.md) for the owner to review and apply.
4. **Android minSdk.** 29, or higher if that simplifies anything.
5. **Play Billing and the relay verifier.** Not answered. They stay under "Needs the user" in the tasks document; the app is built around a

10. **HEVC from the Windows host.** Decided by evidence, below.

### HEVC from the Windows host: comparison and decision

| Question | H.264 | HEVC |
|---|---|---|
| Bitrate for equal quality | baseline | commonly quoted around 30 to 40 percent lower for screen content; not measured here |
| Value to this product | enough on a LAN, where bandwidth is not the limit | matters on relayed sessions, where the tiers are 2, 8 and 20 Mbps (`VideoFallback.swift:3-7`) and the relay is a single region |
| Windows hardware encode through Media Foundation | exposed by NVENC, Quick Sync and AMF encoder MFTs on essentially every GPU; software MFT as fallback | the GPU vendor MFTs expose it on newer parts; availability depends on GPU generation and driver, and the software path may need a store extension; not verified on any machine |
| Android MediaCodec decode | universal | widespread hardware decode, not guaranteed on low end devices; must be detected with `MediaCodecList` |
| Latency | lowest encode cost | similar with low latency settings, slightly heavier encode |
| Licensing and patent exposure | lighter, and the OS or GPU vendor carries the codec | larger, separate pools; using vendor encoders shifts most of it but a distributed app is not outside it; not legal advice, owner to confirm |
| Apple clients | decode both | decode both; the Mac host already defaults to HEVC (`HostModel+Capture.swift:24-26`) |
| Complexity | none | a codec negotiation (`videoCodecs` in the hello), a second parameter set layout (VPS, SPS, PPS), encoder capability probing, and an always-working H.264 fallback |

Decision: not in v1, and not SKIP. The benefit is real only for relayed sessions, while the costs (per-machine encoder availability,
negotiation, licensing question) are paid up front. HEVC is recorded as three small LATER tasks (WIN-124, WIN-131, WIN-132) behind a
capability flag, with H.264 as the encoder that always works. A client that does not declare `videoCodecs` (every shipped iPhone) always gets H.264 from the Windows host.
